# Paso de build explícito para el supervisor

## Contexto

`pnpm tick` (`tsx src/index.ts`) es lo que corre tanto en desarrollo local como en
el cron en vivo (`scripts/run-tick.sh`, generado por `scripts/setup-cron.sh`).
`tsx` interpreta el TypeScript fuente directo en cada invocación — no hay ningún
paso de compilación intermedio. Esto significa que un merge a `main` se refleja
en el comportamiento del supervisor en el próximo tick de cron (hasta 5 minutos
después), sin ningún gate manual de por medio.

Surgió al arrancar la implementación del plan de stacked PRs
(`docs/superpowers/plans/2026-07-28-stacked-prs.md`): aunque ese trabajo se hace
en un worktree aislado (no afecta a `main` hasta el merge), en el momento del
merge el cron de este mismo host levantaría el código nuevo en el siguiente
tick sin que nadie lo haya decidido explícitamente ni haya podido verificarlo
primero.

## Objetivo

Que el proceso que corre el cron (`scripts/run-tick.sh`) ejecute un artefacto
compilado (`dist/`), y que ese artefacto solo cambie cuando alguien corre
`pnpm build` a propósito — nunca como efecto colateral de un `git merge` o de
editar un archivo.

## Decisiones

- **`pnpm tick` (dev) no cambia**: sigue corriendo `tsx src/index.ts` para
  iteración local rápida (dry runs como el de `docs/DESIGN.md` §10) — el gate
  de build aplica solo al camino de producción/cron.
- **Build falla fuerte con errores de tipos**: `noEmitOnError: true` en
  `tsconfig.json` — un `pnpm build` con errores no debe dejar un `dist/`
  parcialmente emitido que parezca válido.
- **`dist/` faltante bloquea el tick, `dist/` desactualizado solo advierte**:
  si `dist/index.js` no existe, el wrapper corta con un mensaje claro antes de
  intentar `node`. Si existe pero algún `.ts` de `src/` es más nuevo (por
  timestamp), solo loguea un `WARN` y sigue corriendo el `dist/` existente —
  bloquear por esto sería propenso a falsos positivos (un `touch`, un checkout
  de git) y el diseño ya prioriza no bloquear en falso sobre logs de rutina
  (ver `docs/BLOCKING.md`).

## Diseño

### 1. `package.json`

Nuevos scripts:

```json
"build": "tsc",
"start": "node dist/index.js"
```

`tsconfig.json` ya tiene `outDir: "dist"` — no hace falta un `tsconfig` separado
para build. `"tick"` no cambia.

### 2. `tsconfig.json`

Agregar `"noEmitOnError": true` a `compilerOptions`.

### 3. `scripts/setup-cron.sh`

El heredoc que genera el wrapper (`$WRAPPER`) cambia su línea final de
`pnpm tick` a:

```bash
if [ ! -f dist/index.js ]; then
  echo "$(date -Is) [cron] dist/index.js no existe — correr pnpm build" >&2
  exit 1
fi
if [ -n "$(find src -newer dist/index.js)" ]; then
  echo "$(date -Is) [cron] WARN: src/ tiene cambios más nuevos que dist/ — considerar pnpm build"
fi
pnpm start
```

(El resto del wrapper — log rotation, `flock`, `source .env` — no cambia.)

### 4. `README.md`

En el paso de setup (línea ~28, junto a `pnpm cron:setup`), agregar una nota:
después de cualquier cambio de código, correr `pnpm build` para que el cron lo
recoja — el cron nunca reconstruye solo.

### 5. Deploy en este host (manual, fuera del repo)

`scripts/run-tick.sh` es generado y gitignored (comentario en `.gitignore`:
"generated by scripts/setup-cron.sh, bakes in a machine-specific PATH") — el
cambio de plantilla en `scripts/setup-cron.sh` no se aplica solo. Hace falta,
una vez mergeado esto:

1. `pnpm build` (para que exista `dist/index.js` la primera vez).
2. `pnpm cron:setup` (re-corre `scripts/setup-cron.sh` con los mismos
   minutos/retención de hoy, regenerando `scripts/run-tick.sh` con la
   plantilla nueva).

## Testing

Sin test automatizado — son cambios de configuración/build/shell, sin lógica
de decisión nueva en `src/`. Verificación manual:

- `pnpm build` seguido de `pnpm typecheck` — confirmar que `dist/index.js`
  existe y es ejecutable (`node dist/index.js`, con un `.env` de prueba,
  produce el mismo log de tick que `pnpm tick`).
- Simular `dist/index.js` faltante (renombrarlo) y correr el wrapper
  actualizado — confirmar que corta con el mensaje esperado sin tocar `node`.
- Simular staleness (`touch` un archivo de `src/`) y correr el wrapper —
  confirmar que loguea el `WARN` y de todas formas corre.

## Fuera de alcance

- Empaquetado/bundling (esbuild, etc.) — `tsc` plano alcanza para este scaffold.
- Build automático disparado por un hook de git (post-merge, etc.) — el punto
  central de este cambio es que el build sea una decisión humana explícita,
  no automática.
