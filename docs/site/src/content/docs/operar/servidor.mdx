Por defecto, ronin descubre todo por polling, con el cron. Con el **servidor de ronin** reacciona casi al instante: a una asignación, a un PR nuevo, actualizado o cerrado, a una review, a un comentario o comando, al label `ronin:auto-merge` o a un CI que termina.

El servidor (servicio `ronin-server`) recibe los webhooks de GitHub. Por cada evento lanza un handler, un proceso aparte que corre solo lo que ese evento puede mover y solo sobre ese issue o PR. Los eventos que llegan juntos sobre lo mismo se agrupan durante `WEBHOOK_DEBOUNCE_MS`. **El tick sigue corriendo** como conciliación: levanta lo que un webhook perdido no hizo.

**Con [la base de datos](/ronin/operar/base-de-datos/)**, el servidor también pone en cola el tick a sus horas (cada `TICK_INTERVAL_MINUTES`, 30 por defecto y editable en Ajustes, desde la hora en punto) y arranca él mismo cada tick y cada handler como un trabajo de la cola. El cron ya no hace falta: `pnpm cron:remove`. Si el servidor no está corriendo, no hay ticks.

El mismo servidor sirve el [tablero](/ronin/operar/tablero/), en un listener aparte que solo ve la tailnet, y el [portal](/ronin/operar/portal/).

## Qué tiene que ser alcanzable

GitHub tiene que llegar al **listener público** (`SERVER_PORT`). Si la máquina no tiene IP pública, exponelo con lo que ya tengas, por ejemplo un túnel y un reverse proxy hacia `127.0.0.1:<SERVER_PORT>`.

El listener público atiende solo `POST /api/webhooks/github` y el portal. Cualquier otra ruta responde 404, aunque el proxy reenvíe todo: **el tablero nunca queda expuesto por ahí.**

## Instalarlo

<Steps>

1. Generá un secreto con `openssl rand -hex 32` y completá `WEBHOOK_SECRET` en `.env`.

2. `pnpm build`: el servidor corre el `dist/` compilado, igual que el cron.

3. `pnpm server:setup` lo instala como servicio systemd `--user` (`ronin-server`), con reinicio automático. `pnpm server:remove` lo saca. Los logs:

   ```bash
   journalctl --user -u ronin-server -f
   ```

4. Exponé el puerto con tu proxy o túnel bajo una URL HTTPS, por ejemplo `https://ronin.example.com`.

5. Registrá el webhook en cada repo de `repos.json`:

   ```bash
   pnpm init-webhooks https://ronin.example.com/api/webhooks/github
   ```

   Suscribe `issues`, `pull_request`, `issue_comment`, `pull_request_review_comment`, `pull_request_review`, `check_suite`, `release` y `workflow_run`. Es idempotente: si el hook ya existe, le actualiza la URL y los eventos en vez de crear otro. Si una versión de ronin suma un evento, volvé a correrlo.

</Steps>

Para confirmar que GitHub llega, mirá en cada repo *Settings → Webhooks → Recent Deliveries*: tienen que dar 202.

<Aside type="tip">
Sin la base de datos, con el servidor andando, bajale la frecuencia al cron en vez de sacarlo: `pnpm cron:setup 30`, cada 30 minutos. Los webhooks pueden perderse (el túnel caído, un reinicio). Con la base, el cron se saca: el servidor corre los ticks.
</Aside>

## Al desplegar una versión nueva

```bash
git pull && pnpm install --frozen-lockfile && pnpm build && systemctl --user restart ronin-server
```

El proceso no recarga `dist/` solo. Reiniciarlo no corta los handlers que estén corriendo.

## Cuánto tarda

ronin mide cada request de su API y cada tick:

- **En el navegador:** cada respuesta de la API trae la cabecera `Server-Timing` con el total y el tiempo en GitHub, también por operación (`github:getItemDiscussions`, por ejemplo: la función de ronin que hizo la llamada). En las herramientas de desarrollo aparece en la pestaña *Timing* del request.
- **En el log:** un request que pasa de `SLOW_REQUEST_MS` (500 ms por defecto) deja una línea `slow_request` con su ruta, su estado y en qué se fue el tiempo. Cada `tick_complete` trae lo que tardó cada paso, el descubrimiento, los trabajos y el tiempo en GitHub.
- **El clic:** el tablero mide cuánto pasa desde que alguien comenta, aprueba, manda una revisión o corre una acción hasta que lo ve en la página, y se lo manda al servidor. En el resumen aparece como `CLIC comentar`, `CLIC decision`, etc.
- **El resumen:** cada 10 minutos el servidor guarda un resumen por ruta en `logs/timings/<día>.jsonl`. `pnpm timings [días]` arma la tabla de los últimos días (7 por defecto), con las rutas y los ticks, y en cada uno las operaciones de GitHub que más tiempo se llevan:

```bash
pnpm timings 7
```

Sirve de línea base para comparar antes y después de un cambio.
