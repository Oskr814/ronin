ronin pasa de guardar sus datos en archivos a guardarlos en Postgres de a un módulo por vez ([#235](https://github.com/Oskr814/ronin/issues/235), etapa 2). Por ahora están en la base:

| Módulo | Qué | Para pasarlo |
|---|---|---|
| **Ajustes** | Los valores cambiados desde el tablero, el modelo y el esfuerzo de cada tipo de tarea, el plan de cada cuenta de Claude y el registro de cambios. | `pnpm db:import-ajustes` |
| **Despliegues** | Cada release que publicó ronin: qué llevó, quién y cómo terminó su workflow. | `pnpm db:import-despliegues` |
| **Reuniones** | Cada reunión: sus propuestas, lo que se creó y su actividad. Las notas y el archivo subido siguen en `MEETINGS_DATA_DIR`. | `pnpm db:import-reuniones` |
| **Portal** | Las cuentas y los pedidos, con su conversación y su actividad. Las imágenes y los diffs siguen en `PORTAL_DATA_DIR`. | `pnpm db:import-portal` |
| **Estado local** | Lo que ronin recuerda de cada repo entre ticks: los issues que tomó, los comentarios que ya atendió, por qué bloqueó cada issue, los checks que espera. | `pnpm db:import-estado-local` |

Todo lo demás sigue en sus carpetas.

Con la base, además, **el servidor corre los ticks**: los pone en cola a sus horas y los arranca, igual que los handlers de los webhooks. Hay que sacar el cron (`pnpm cron:remove`); si queda, no hace nada.

**Es opcional mientras dura la etapa.** Sin `DATABASE_URL`, ronin sigue con los archivos como siempre.

## Activarla

<Steps>

1. En `.env`, una contraseña y un puerto libre de esta máquina para Postgres, y la URL que apunta a ellos:

   ```bash
   RONIN_PG_PASSWORD=<contraseña>
   RONIN_PG_PORT=<puerto>
   DATABASE_URL=postgres://ronin:<contraseña>@127.0.0.1:<puerto>/ronin
   ```

2. Levantar Postgres con `compose.postgres.yml`. Escucha solo en `127.0.0.1` y guarda sus datos en el volumen `ronin-pg`:

   ```bash
   docker compose -p ronin-db -f compose.postgres.yml --env-file .env up -d
   ```

3. Copiar los datos de los archivos a la base, un módulo por vez. Cada script crea las tablas, compara lo copiado con los archivos y termina con error si algo no coincide. Se puede correr de nuevo sin duplicar nada:

   ```bash
   pnpm db:import-ajustes
   pnpm db:import-despliegues
   pnpm db:import-reuniones
   pnpm db:import-portal
   pnpm db:import-estado-local
   ```

4. Desplegar y reiniciar el servidor. Al arrancar pone la base al día (`pnpm db:migrate` hace lo mismo a mano); el tick y los workers toman `DATABASE_URL` en su próxima corrida.

</Steps>

Los archivos quedan como estaban, de respaldo: desde ahí ya no se escriben.

**Con la base ya activa,** un módulo nuevo empieza a usarla apenas se despliega: hay que correr su `pnpm db:import-<módulo>` antes de desplegar, o lo que había en su archivo no se ve hasta que se corra.

## Volver atrás

Sacar `DATABASE_URL` de `.env` y reiniciar el servidor: ronin vuelve a los archivos. Lo que se cambió en Ajustes mientras estaba la base no está en los archivos.

<Aside type="caution">
Si la base no responde, ronin no se detiene: cada proceso usa los valores de `.env`, como cuando el archivo de Ajustes no se puede leer, y lo dice en el log. Guardar un cambio en Ajustes falla hasta que vuelva.
</Aside>

## Respaldo

La base es la única copia de lo que guarda. Hasta que la etapa 5 sume los respaldos automáticos, un `pg_dump` periódico:

```bash
docker exec ronin-postgres pg_dump -U ronin ronin > ronin-$(date +%F).sql
```

## Las pruebas

Las pruebas de los repositorios corren contra un Postgres real. En el CI hay uno; en local, `compose.test.yml` levanta uno descartable:

```bash
docker compose -f compose.test.yml up -d
TEST_DATABASE_URL=postgres://ronin:ronin@127.0.0.1:54329/ronin_test pnpm test
```

Sin `TEST_DATABASE_URL`, esas pruebas se saltan y el resto corre igual.
